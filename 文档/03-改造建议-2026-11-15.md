## 1. 第一阶段：优先修复的稳定性问题

### 1.1 修复技能浏览页面的异步请求竞态

**优先级：P1**

**涉及位置：** `revamp/launcher.js` 中 `SkillBrowse` 相关的
`load()`、`loadHome()` 及其调用逻辑（此前审查约在 2520
行附近，需按当前代码重新定位）。

**问题说明：**

用户快速切换工作区、页面或筛选条件时，可能同时发出多个请求。如果较早发出的请求反而最后返回，它可能把旧数据写进当前页面，造成列表闪回、内容错乱或显示错误工作区的数据。

**修改要求：**

-   检查所有会更新技能浏览页面状态的异步请求。
-   为每次请求增加可识别的请求编号（request ID），或使用
    `AbortController` 取消已经过期的请求。
-   只有"当前仍然有效"的请求可以更新页面数据、错误状态和 loading 状态。
-   页面组件卸载时，取消仍在进行的请求，或确保其结果不会再更新状态。
-   不要只保护成功结果；旧请求返回的错误也不能覆盖新请求的正常状态。
-   如果同一页面存在多个独立请求，应分别管理，避免一个请求错误地取消另一个无关请求。

**验收标准：**

1.  快速连续切换两个或多个工作区，最终显示的数据必须属于最后选择的工作区。
2.  先发出的请求即使最后返回，也不能覆盖当前页面。
3.  页面离开后，旧请求不能再触发过期的界面更新。
4.  正常加载、空结果和请求失败时，loading 状态都能正确结束。

### 1.2 让技能替换安装具备失败恢复能力

**优先级：P1**

**涉及文件：** `lib/importer.js`（此前审查约在 35
行附近，需重新定位实际安装/替换流程）。

**问题说明：**

目前审查到的流程大致是：先把旧技能移入回收站，再准备新技能暂存目录、写入文件并重命名。如果中途写文件或移动目录失败，可能出现旧版本已经被移走、新版本却没有安装成功的情况。

**修改要求：**

-   先完成新技能内容的校验，并在独立的临时目录中准备完整的新版本。
-   确认临时目录内容齐全、关键文件可读后，再进入替换阶段。
-   替换时保留旧版本的可恢复路径；只有新版本成功进入正式位置并通过必要检查后，才清理旧版本。
-   如果替换过程失败，应尽力恢复旧版本到原位置。
-   临时目录应在成功或失败后按规则清理，不能误删用户原有技能目录。
-   注意处理目标目录已存在、临时目录重名、进程中断和文件移动失败等情况。
-   保持现有安装目录规则、技能格式和用户数据兼容。

**验收标准：**

1.  正常安装新技能成功。
2.  正常替换旧技能成功。
3.  模拟新文件写入失败时，旧技能仍然可用。
4.  模拟新目录移动失败时，旧技能能够恢复，或系统明确报告恢复失败及保留位置。
5.  不会因为清理临时目录而删除旧技能或其他无关目录。

### 1.3 核实本地 API 的访问边界

**优先级：P1（先调查，再决定是否修改）**

**涉及文件：** `lib/api.js`，重点检查
`isSameOrigin()`、服务监听地址、`/import-path`
及会修改本地文件或技能状态的路由。

**问题说明：**

此前静态审查发现，`isSameOrigin()` 对缺少 `Origin` 和 `Origin: null`
的请求会放行。这可能是为了兼容本地非浏览器调用，也可能形成需要进一步确认的安全边界问题。插件接口具备读取本地文件、安装或删除技能、修改权限等能力，因此不能仅凭这一段代码判断安全与否。

**Agent 必须先调查：**

-   API 实际监听 `127.0.0.1`、`localhost`、`0.0.0.0` 还是其他地址。
-   是否可能被局域网中的其他设备访问。
-   Harness 是否在 API 外层提供身份验证或访问控制。
-   哪些路由会读取文件、写入文件、删除技能或更改权限。
-   `Origin` 缺失或为 `null` 的请求，是否确实来自受信任的本地调用方。
-   `/import-path`
    是否允许调用者提交任意本地绝对路径；是否有路径范围、权限或用户确认保护。

**修改要求：**

-   先形成简短的威胁模型和现状说明，再提出最小必要修复。
-   如果 API 不需要被局域网访问，应优先确认并限制为 loopback 监听。
-   对会改变本地文件或技能状态的请求，确认存在适当的调用方校验或用户授权。
-   不要简单地把所有无 `Origin`
    请求一律拒绝；这可能破坏合法的本地调用。应先确认调用方式，再设计兼容的保护措施。
-   对用户提供的路径做规范化和边界检查，避免路径穿越或意外访问不允许的位置。
-   不要在日志或错误信息中泄露不必要的本地敏感路径。

**验收标准：**

1.  文档说明 API 的监听范围、调用方和信任边界。
2.  不受信任的网页或远程设备不能未经授权执行敏感操作。
3.  合法的 Harness 本地调用仍然正常工作。
4.  路径校验能阻止越界访问，并有对应测试。
5.  如果某项安全结论依赖 Harness
    的外部保护，必须明确写出证据或验证方式。

## 2. 第二阶段：修复界面布局与操作体验

### 2.1 避开 macOS 窗口左上角的红黄绿控制按钮

**优先级：P1（针对用户当前反馈）**

**涉及文件：** 优先检查 `revamp/market.css`
及负责窗口外框、顶部栏和侧边导航的组件。

**问题说明：**

插件界面左上角与 macOS
原生窗口控制按钮区域重叠。窗口较小时更明显，窗口放大后不明显。用户确认这是运行在
DeepSeek Harness 中的插件，不是独立 macOS 应用。

**修改要求：**

-   先确认真正与原生窗口按钮重叠的是哪一个元素：插件整体容器、侧边栏、品牌标识还是顶部栏内容。
-   不要直接给整个 `.ss_panel`
    增加左边距；这可能让弹窗整体偏移、变窄或破坏居中。
-   优先只给左上角受影响的内容区域增加安全间距。
-   在合适的 CSS 范围内建立变量，例如
    `--macos-titlebar-safe-left`，避免把同一个像素值散落在多个规则中。
-   此前建议在 `@media (max-width: 1100px)` 下测试将 `.sk_side` 左侧
    padding 从 `18px` 增加到约 `80px`。**80px
    仅是试验起点，不是已验证的最终值。** Agent
    应根据真实窗口截图和布局测量调整。
-   检查窗口宽度变化时，安全间距是否会导致导航挤压、换行或横向溢出。
-   如果 Harness 有正式提供的标题栏安全区变量或
    API，先核实其存在和用法；没有证据时不要编造。

**验收标准：**

-   在窗口较窄和较宽时，插件内容都不与红黄绿按钮重叠。
-   不会为了避开按钮而让整个面板明显偏离中心。
-   左侧导航、品牌标识和顶部内容不会互相遮挡。
-   窗口缩放时布局稳定，没有突然跳动或横向滚动条异常。

### 2.2 检查响应式布局断点

**涉及文件：** `revamp/market.css`。

此前检查到的规则包括：

-   `.ss_panel` 使用固定最大宽度和视口限制。
-   `@media (max-width: 1100px)` 将主布局改为纵向，侧栏变为横向导航。
-   `.sk_nav` 已设置横向滚动相关属性。
-   `@media (max-width: 760px)` 还有更窄屏规则。

**修改要求：**

-   不要只针对一个宽度调样式；要检查断点前后是否出现布局突然变形。
-   确认侧栏横向导航在窄窗口中可以正常滚动，按钮不会被压缩到无法辨认。
-   检查顶部栏、搜索框、筛选器、弹窗内容和底部操作区是否溢出。
-   尽量复用已有断点，避免新增大量互相重叠的媒体查询。
-   不要为了"看起来适配"而隐藏重要操作入口。

**建议测试宽度：**

`1400px`、`1100px`、`1000px`、`800px`、`760px`、`600px`。

如果 Harness 的实际窗口尺寸范围不同，应以真实运行环境为准。

### 2.3 补全弹窗焦点管理和键盘操作

**优先级：P2**

**涉及文件：** `revamp/footer.js`、`revamp/launcher.js` 中的对话框实现。

**问题说明：**

此前检查到部分弹窗已有 `role="dialog"`、`aria-modal="true"` 和 ESC
关闭，但没有发现完整的焦点管理。

**修改要求：**

-   弹窗打开时，将键盘焦点移动到弹窗内合适的控件。
-   按 Tab 和 Shift+Tab 时，焦点应留在弹窗内部。
-   弹窗关闭后，把焦点还给打开弹窗的原控件。
-   ESC 关闭行为应与当前产品交互保持一致。
-   如果弹窗内有危险操作，不要让默认焦点直接落在"删除"或"确认"等高风险按钮上。
-   不要只添加 ARIA 属性却没有真正实现键盘行为。

**验收标准：**

可以仅使用键盘打开弹窗、操作弹窗、关闭弹窗，并且关闭后焦点回到合理位置。

## 3. 第三阶段：修正文案与统一交互反馈

### 3.1 修正本地路径安装的大小限制提示

**涉及文件：** `lib/api.js` 及相关错误提示位置。

**问题说明：**

此前审查发现，某处提示建议用户改用本地路径安装，并称本地路径没有大小限制。但本地目录读取逻辑仍有文件大小、总大小、文件数量和目录深度限制。

已发现的限制值包括：

-   单个文件约 64 MB。
-   总大小约 256 MB。
-   最多约 500 个文件。
-   目录深度也有限制。

Agent
应重新核实当前代码中的真实限制值，不能直接把上述数字当成永远不变的常量。

**修改要求：**

将容易误导用户的"本地路径没有大小限制"改为准确表达，例如：

> 本地路径安装不受浏览器上传请求大小限制，但仍受本地文件大小、文件数量和目录深度限制。

如果限制值可能变化，优先引用实际配置或统一常量，不要在多个文案中重复写死数字。

### 3.2 统一加载、成功、失败和空状态

**优先级：P2**

**修改要求：**

-   页面加载时显示明确的 loading 状态。
-   没有搜索结果时显示"没有找到匹配的技能"，并提供清除搜索条件的方式。
-   加载失败时说明发生了什么，并在适合的地方提供重试。
-   安装、删除、导入等操作成功或失败时，使用一致的提示样式。
-   避免重复点击导致同一操作被执行多次。
-   不要让 loading 状态在异常情况下永久停留。

**验收标准：**

主要页面至少覆盖正常、有数据、无数据、加载中、失败五种状态；重要操作有明确结果反馈。

**优先级：P3**

-   避免同一个错误被多层重复弹出。
-   对可恢复错误提供重试或恢复说明。

## 8. 本轮范围建议
